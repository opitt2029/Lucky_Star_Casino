## 0. 四個 30 秒版（先背這四段）

**Q：Java 21 有用虛擬執行緒嗎？**
> 「有 Java 21，但**沒有開**虛擬執行緒，這是刻意的。我們壓測顯示瓶頸在 HikariCP 連線池——排隊 49 條、取連線最長 1.19 秒——不在執行緒數。虛擬執行緒放大的是併發**進入量**，不會放大**下游容量**，開了只是把排隊從 Tomcat 佇列搬到連線池佇列，P99 反而更差。而且 Java 21 的虛擬執行緒在 `synchronized` 內阻塞會 pin 住 carrier 執行緒，JDBC driver 和 Kafka client 都會踩到。Java 24/25 的 JEP 491 才修掉這個限制。」

**Q：為什麼用 Spring Boot 而不是 JPA？**
> 「這兩個其實不是二選一——Spring Boot 是應用框架，JPA 是持久化規格，我們兩個同時用。真正的取捨是 **Spring Data JPA vs 原生 JDBC**，而我們是**按熱路徑分工**：90% 的 CRUD 走 JPA 省開發時間；錢包扣款那條熱路徑走 `JdbcTemplate` 手寫 `UPDATE ... WHERE 守衛 ... RETURNING`，因為那要的是**語句級原子性**，JPA 的讀改寫模型表達不出來。兩者掛同一個 DataSource，JdbcTemplate 會 join 同一筆交易，交易邊界不變。」

**Q：Redis 怎麼連的？**
> 「Spring Boot 預設的 **Lettuce**，走 **shared native connection 而不是連線池**。因為 Lettuce 底層是 Netty、執行緒安全，一條連線就能 pipeline 多工；而 Redis 執行命令本來就是單執行緒，開池不會提升它的處理能力，反而多了池的借還競爭。我們對付網路往返的方式不是加連線，是**把多步操作壓成 Lua 腳本**——全專案 5 支，Lua 在 Redis 單執行緒內原子執行，等於免費的交易。」

**Q：你們有做多級快取嗎（L1 記憶體 + L2 Redis）？**
> 「知道這個架構，但我們**刻意沒做 L1**。L1 買的是延遲、付的是一致性——每個 JVM 一份 L1，寫入要靠 Pub/Sub 廣播失效或短 TTL 硬扛陳舊。而我們 Redis 裡沒有一個 key 是『讀多寫少的熱點快取』：排行榜是**主儲存**、停用標記和 JWT 黑名單是**安全機制**、限流令牌桶是**全域計數**、捕魚 session 是**讀改寫狀態**——全都禁不起陳舊，加 L1 只會製造 bug。唯一的純快取是風控 RTP，但它每 2 秒才被排程刷一次，加 L1 收益趨近於零。」

## 1. 虛擬執行緒：我們沒開，以及為什麼「沒開」才是對的

### 1.1 事實盤點（可當場驗證）

全 repo 搜尋 `virtual` / `ofVirtual` / `newVirtualThreadPerTaskExecutor` / `spring.threads.virtual`
→ **程式碼與設定檔零命中**。

我們七個服務實際的執行緒模型：

| 服務 | Web 模型 | 執行緒模型 |
|---|---|---|
| gateway-service | **WebFlux / Netty**（Spring Cloud Gateway） | event loop，少量 I/O 執行緒；**本來就不需要也不該開虛擬執行緒** |
| member / wallet / game / rank / admin / notification | **Spring MVC / Tomcat** | **平台執行緒池，預設 200 條**（`server.tomcat.threads.max` 七個服務都沒顯式設定） |

也就是 6 × 200 = **1,200 條 OS 平台執行緒**是併發處理能力的天花板。

### 1.2 「最該用」的地方在哪

`backend/game-service/src/main/java/com/luckystar/game/config/WalletClientConfig.java:25`

```java
@Bean
public RestClient walletRestClient(RestClient.Builder restClientBuilder, ...) {
    return restClientBuilder.baseUrl(baseUrl)
            .defaultHeader("X-Internal-Secret", internalSecret)
            .build();   // ← 同步阻塞 HTTP
}
```

每一次老虎機 spin，game-service 要對 wallet-service 發 **2 次同步阻塞 HTTP**（`debit` 下注、`credit` 派彩）。Tomcat 執行緒在 socket read 上乾等——這是虛擬執行緒的**教科書級適用場景**（thread-per-request + 阻塞 I/O）。

開啟它在 Spring Boot 3.3.5 只要一行：

```yaml
spring:
  threads:
    virtual:
      enabled: true
```

### 1.3 那為什麼不開？兩個硬理由

#### 理由 A：我們的瓶頸不是執行緒，是 DB 連線（有實測數字）

`backend/game-service/src/main/resources/application.yml` 的註解就是壓測結論：

```yaml
# T-090 壓測（2026-07-21）發現此池尖峰滿載、排隊等待達 49 條執行緒、取連線最長 1.19s，
# 是老虎機 P99 延遲主因。首輪保守調 10→24；2026-07-22 ... 再上調 24→40
maximum-pool-size: 40
```

- 虛擬執行緒解決的是「**執行緒稀缺**」：一條平台執行緒 ≈ 1 MB stack，開幾萬條會爆記憶體。
- 我們稀缺的是「**連線**」：PostgreSQL `max_connections = 200`，我們的預算是 game 40 + wallet 40 + rank 10 + admin 5 = 95。

開了虛擬執行緒的實際結果是：**更多請求更快地擠到 HikariCP 門口排更長的隊**。
總吞吐不變（受限於 DB 交易容量，JFR 實測 ≈ 550–600 筆/秒），但排隊時間拉長 → **P99 更爛**。

> 這叫「**把排隊往下游推**」，是效能調校最常見的假優化。
> 對照 `13-壓測與效能調校.md` 的同一個教訓：「連線池調大只是把隊伍從應用內搬到資料庫內，總延遲不變。」

#### 理由 B：Java 21 的 pinning 正好會咬到我們的熱路徑

Java 21 虛擬執行緒的致命限制：**在 `synchronized` 區塊內阻塞會「釘住」(pin) carrier 執行緒**，無法卸載。carrier 池預設只有 CPU 核心數那麼多條。

而我們熱路徑上一路都是 `synchronized` 密集的成熟程式庫：

- **JDBC driver**（pgjdbc / mysql-connector-j 內部仍有 `synchronized` 區塊）
- **HikariCP** 的部分內部路徑
- **Kafka client**

一旦虛擬執行緒阻塞在這些地方 → carrier 被釘死 → 幾條 carrier 全佔滿 → **整個服務近乎停擺**。
症狀是「吞吐突然崩掉但 CPU 很低」，**極難除錯**。

### 1.4 什麼時候我們「該」開？（面試官追問時的回答）

三個條件同時成立才值得：

1. **瓶頸確認在執行緒數而非下游有界資源**（Tomcat 執行緒池飽和、但 DB 連線池還有餘裕）
2. **升到 Java 24+**，pinning 問題消失
3. **熱路徑以 I/O 等待為主**（我們符合，game→wallet 兩次同步 HTTP）

現在只有第 3 條成立。所以答案是「知道、評估過、條件不成立」。

> **面試怎麼講**
> 「虛擬執行緒最適合 thread-per-request 又大量阻塞 I/O 的場景，我們 game→wallet 每局兩次同步 HTTP 正是這種。但我們沒開，因為壓測證明瓶頸在連線池不在執行緒——開了只會讓更多請求更快撞到同一道門。我把它記成『瓶頸在有界資源時，放大併發進入量只會惡化 P99』。另外 Java 21 的 pinning 會咬到 JDBC driver，那是我們最不能出事的路徑。」

## 2. Java 21 vs Java 25（都是 LTS，差在哪）

| 面向 | **Java 21**（2023-09 LTS，我們用的） | **Java 25**（2025-09 LTS） |
|---|---|---|
| 虛擬執行緒 | GA (JEP 444)，**但 `synchronized` 內阻塞會 pin carrier** | **JEP 491 修掉 pinning**（Java 24 落地、25 承接）——monitor 阻塞也能卸載 |
| Scoped Values | 預覽 | 正式（虛擬執行緒版的 ThreadLocal 替代品） |
| Structured Concurrency | 預覽 | 仍在預覽（API 反覆調整） |
| 物件頭 | 傳統 12/16 bytes | **Compact Object Headers 轉正式並預設啟用**，堆記憶體省約 10–20% |
| 啟動 | — | AOT class loading（Project Leyden 首波） |
| Pattern matching | record patterns、switch pattern matching 皆 GA | 同上，再加語法便利性 |

### 對我們專案，最實質的差別只有一個：**pinning**

Java 25 之後，上面 §1.3 的「理由 B」整條消失。也就是：

> **Java 21 = 虛擬執行緒「能用但有地雷」；Java 24/25 = 虛擬執行緒「可以無腦用」。**

這才是版本號背後真正的分水嶺，不是「都是 LTS 所以差不多」。

### 那為什麼還在 21？誠實答案：**被 Spring Boot 的支援線綁住**

`pom.xml:10` 我們是 **Spring Boot 3.3.5**，baseline Java 17、官方測試支援到 Java 22/23 區間，**不含 25**。
要跑 Java 25 得先升 Spring Boot（3.5+/4.x），連帶 Spring Cloud 2023.0.3 → 新版本矩陣、Spring Security、Spring Cloud Gateway 全部要跟著動——那是一次跨七個服務的升級專案，不是順手做的事。

> **面試怎麼講**
> 「我們選 21 是跟著 Spring Boot 3.3.5 的官方支援線走，不是隨便挑。我知道 25 最有價值的是 JEP 491 把虛擬執行緒的 pinning 修掉了——那才是我們真正想升的理由。但升級成本是整個 Spring Cloud 版本矩陣加七個服務回歸，要當專案規劃不是順手改個數字。」

## 3. 「為什麼用 Spring Boot 而非 JPA」——先糾正前提，再談真正的取捨

### 3.1 這題的前提是錯的（禮貌地指出來，這是加分不是扣分）

| | 是什麼 | 解決什麼問題 | 層次 |
|---|---|---|---|
| **Spring Boot** | 應用**框架** / 自動組態 / starter 依賴管理 | 「怎麼把一個 Java 應用組裝起來跑」 | 應用層 |
| **JPA** | Java Persistence API，一份**規格**（`jakarta.persistence`），Hibernate 是實作 | 「Java 物件怎麼對映到資料表」 | 持久化層 |

兩者**正交**，不是替代關係。我們是**兩個同時用**：

```
backend/*/pom.xml:28   spring-boot-starter-web        ← Spring Boot
backend/*/pom.xml:34   spring-boot-starter-data-jpa   ← Spring Data JPA (Hibernate)
```

六個服務都有（notification-service 只有 web + websocket，它不碰 DB）。

### 3.2 面試官真正可能想問的三題

#### (A) Spring Boot vs 傳統 Spring Framework（XML 組態）
Boot 全面勝出，沒有辯論空間。理由：自動組態、內嵌 Tomcat、starter 統一版本管理（我們根 `pom.xml` 一處管七個服務的 Spring Cloud / JJWT 版本）、Actuator 開箱即用（`/actuator/prometheus` 就是靠它，壓測全靠這條）。

#### (B) **Spring Data JPA vs 原生 JDBC / MyBatis** ← 這才是有料的題

**我們的答案是「分工」不是「二選一」。**

**用 JPA 的地方** — `backend/wallet-service/.../postgres/entity/Wallet.java:39`：
```java
@Version
@Column(name = "version", nullable = false)
private Long version;   // 一個 annotation 換到樂觀鎖，
                        // Hibernate 自動在 UPDATE 補 WHERE version = ?
```
credit（入帳）、gift（贈幣）、凍結等寫入方全走這條。開發速度快、防超扣不用自己寫。

**用原生 JDBC 的地方** — `backend/wallet-service/.../postgres/repository/WalletDebitDao.java`（扣款熱路徑，T-090 B2）：
```java
private static final String PG_CONDITIONAL_DEBIT = """
        UPDATE wallets
           SET balance = balance - ?, version = version + 1, updated_at = CURRENT_TIMESTAMP
         WHERE player_id = ?
           AND balance - frozen_amount >= ?                          -- 防超扣守衛
           AND NOT EXISTS (SELECT 1 FROM wallet_transactions t
                           WHERE t.idempotency_key = ?)              -- 冪等預檢
        RETURNING balance
        """;
```

**為什麼這段非原生 SQL 不可**（`WalletDebitDao.java:23-25` 的 Javadoc 已寫明）：

> 為什麼用 JDBC 而非 JPA：`RETURNING` / `ON CONFLICT` 是**語句級原子性**的關鍵，**JPA 的讀改寫模型表達不了**。

拆開講：

| | JPA | 這句原生 SQL |
|---|---|---|
| 模型 | read-modify-write：`SELECT` 出 entity → 改 Java 物件 → flush 時 `UPDATE` | 單一 `UPDATE` 語句 |
| 原子性 | 「取出」到「寫回」之間**必然有時間差**，靠 `@Version` 事後偵測衝突 | 守衛與扣款壓在同一語句，由**行鎖**保證，中間**沒有窗口** |
| 往返次數 | 4 次（冪等 SELECT、載入錢包 SELECT、UPDATE wallets、INSERT 流水） | **2 次** |
| 併發輸家 | 拋 409 樂觀鎖例外 | 回 0 列 → 呼叫端補查區分「冪等命中／餘額不足」 |

**還有一個常被誤解的關鍵細節**（`WalletDebitDao.java:83-85`）：
`JdbcTemplate` 掛在**同一個 `postgresDataSource`** 上，所以 `JpaTransactionManager` 會讓它 join `@Transactional(postgresTransactionManager)` 的**同一條連線與同一筆交易**——
**JPA 和原生 JDBC 混用不會破壞交易邊界。**

#### (C) 「所以哪個比較好？」——判準表

| 場景 | 選什麼 | 為什麼 |
|---|---|---|
| CRUD、關聯查詢、後台管理 | **Spring Data JPA** | 開發速度 3–5 倍差距，`@Version`、髒檢查、一級快取全部免費 |
| 帳務熱路徑、要語句級原子性 | **原生 JDBC** | `RETURNING` / `ON CONFLICT` / 條件 UPDATE，JPA 表達不出來 |
| 複雜報表、多表聚合 | **原生 SQL / MyBatis** | JPQL 寫聚合又醜又慢，N+1 地雷多 |
| 團隊要精確控制每一句 SQL | **MyBatis** | 國內金融／遊戲業常見選擇 |

**結論：對「線上賭場帳務系統」，我們的混用是對的。** 帳務正確性 > 開發速度，但只有 2 支 SQL 值得付出手寫成本，其餘 90% 的 CRUD 用 JPA 省下的時間更值錢。

> **面試怎麼講**
> 「我先確認一下——Spring Boot 是應用框架、JPA 是持久化規格，這兩個我們其實同時在用。如果您問的是 Spring Data JPA 跟原生 JDBC 怎麼選，我們是按熱路徑分工的：90% CRUD 走 JPA，扣款那條走 JdbcTemplate 手寫 `UPDATE ... WHERE 餘額守衛 AND NOT EXISTS 冪等檢查 ... RETURNING`。因為那需要語句級原子性——JPA 是讀出來改再寫回去，中間一定有窗口。而且兩者共用同一個 DataSource，JdbcTemplate 會 join 同一筆交易，交易邊界不變。」

## 4. Redis 持久化：快照到底存在哪

面試官問「快照」可能指兩件事，兩個都要會答。

### 4.1 Redis 的持久化（RDB / AOF）

設定在 `docker-compose.yml:50-63`：

```yaml
redis:
  image: redis:7
  container_name: lucky-star-redis
  restart: always
  command: ["redis-server", "--appendonly", "yes"]   # ← 開 AOF
  volumes:
    - lucky_redis_data:/data                          # ← named volume 持久化
```

**檔案實際位置：**

| 檔案 | 內容 | 何時寫 |
|---|---|---|
| `/data/dump.rdb` | **RDB 快照**：整份記憶體的二進位壓縮鏡像 | redis:7 內建預設 `save 3600 1 / 300 100 / 60 10000`——1 小時內 1 次寫、或 5 分鐘內 100 次、或 1 分鐘內 1 萬次，就 fork 子行程存檔 |
| `/data/appendonlydir/appendonly.aof.*.base.rdb`<br>`appendonly.aof.*.incr.aof`<br>`appendonly.aof.manifest` | **AOF**：Redis 7 的 multi-part 格式，逐筆記錄寫入命令 | `appendfsync everysec`（預設）→ 每秒 fsync，**最差損失 1 秒寫入** |

查驗指令：
```bash
docker volume inspect lucky_redis_data              # 看主機上的 Mountpoint
docker exec lucky-star-redis ls -la /data           # 直接看檔案
docker exec lucky-star-redis redis-cli info persistence   # rdb_last_save_time / aof_enabled
```

**容易答錯的細節**：AOF 開啟時，**Redis 重啟是從 AOF 還原，不是 RDB**（AOF 較新較完整）。RDB 仍照 save 規則寫，用於備份、`BGSAVE`、主從複製。

### 4.2 為什麼我們非開 AOF 不可（`docker-compose.yml:54-60` 的註解，這是踩過的雷）

> `redis:7` 預設只做 RDB 快照且寫在容器內部 `/data`，沒掛 volume 時容器一重建資料就全歸零。本專案有兩類資料禁不起這件事：
> - `rank:*` 排行榜 ZSET —— **Redis 是「主儲存」不是快取**，DB 只有每日快照且無回填程式
> - `disabled:player:*` 後台停用標記 —— 無 TTL、只靠 key 存在與否判定，清空等於**所有被停用的玩家自動解封**（安全問題）

**這是全篇最重要的一句話**：**判斷要不要持久化，先問「Redis 對這份資料是快取還是主儲存」**。
純快取掉了重建就好；主儲存掉了是**資料遺失**。

### 4.3 業務層的每日快照（另一種「快照」）

`backend/rank-service/.../scheduler/DailyRankSnapshotScheduler.java:16`
```java
@Scheduled(cron = "0 0 0 * * *", zone = "Asia/Taipei")
```
每天 00:00 把錢包餘額落地成 Postgres 的 `rank_daily_snapshots`。這是**業務層的災難復原點**——Redis 真的被 `down -v` 砍掉時，靠 `tools/reconciliation/rebuild-rank-redis.mjs` 從 DB 重建。

**但要老實說限制**：重建腳本只涵蓋 `rank:daily:winnings` 與 `rank:global:coins` 兩個 ZSET；
`rank:game:*`（各遊戲淨利/局數/勝場）、`rank:player:*`（暱稱/頭像）、`rank:friend:*` **沒有重建路徑**，清掉只能靠新事件慢慢補。

> **面試怎麼講**
> 「我們 Redis 開了 AOF everysec 加 named volume。判準是『Redis 對這份資料是快取還是主儲存』——我們排行榜 ZSET 是主儲存、後台停用標記是安全機制，這兩類掉了就是資料遺失和安全事故，不是重算一下就好。代價是每秒一次 fsync，換的是最差只損失 1 秒。另外我們業務層還有每日快照落地到 Postgres 當災難復原點，不過我要老實說重建腳本只涵蓋兩個 ZSET，其他幾組還沒有回填路徑。」

## 5. 「Redis 還需要連線」——我們怎麼連、怎麼省往返

面試官這句話的意思是：**Redis 是行程外的獨立網路服務，每次操作都是一次 TCP 往返**，不像本地記憶體直接讀。所以要答三層：客戶端、連線模型、往返成本怎麼壓。

### 5.1 客戶端：Lettuce（Spring Boot 預設）

```
backend/{member,wallet,game,rank,admin}/pom.xml   spring-boot-starter-data-redis
backend/gateway-service/pom.xml:52                spring-boot-starter-data-redis-reactive
```

gateway 用 reactive 版是因為它是 WebFlux——**阻塞式 Redis 呼叫會卡死 Netty event loop**，這是 WebFlux 的鐵則。

### 5.2 連線模型：**共用單一連線，不是連線池**

我們**沒有引入 `commons-pool2`**，所以 `LettuceConnectionFactory` 走預設的 `shareNativeConnection = true`：

> **所有 `StringRedisTemplate` 操作共用「同一條」TCP 連線**，靠 Netty 的 pipelining 多工。

**為什麼這樣反而是對的**（很多人答錯的點）：

1. Redis **執行命令是單執行緒**的——開 50 條連線不會讓 Redis 跑得更快
2. Lettuce 底層是 Netty、**執行緒安全**，多個 Java 執行緒可同時往同一條連線塞命令，回應按序回來
3. 少了連線池 = 少了池的借還鎖競爭

**例外**（這些會另外取得專屬連線）：阻塞命令（`BLPOP`）、事務（`MULTI/EXEC`）、Pub/Sub、`SCAN` 游標
（我們的 `FishingSessionStore.listPlayerIds()` 就是 `SCAN`）。

**什麼時候才該開池**：大量使用阻塞命令或事務時。開法是加 `commons-pool2` 依賴 + `spring.data.redis.lettuce.pool.*`。

> **對照組**：Jedis 是**同步阻塞、非執行緒安全**的客戶端，所以用 Jedis **一定要開連線池**。
> 「Lettuce 不用池、Jedis 一定要池」是這題的標準答案分界線。

### 5.3 連線設定

各服務 `application.yml`：
```yaml
spring:
  data:
    redis:
      host: ${REDIS_HOST:localhost}   # compose 裡是 "redis"，走 docker 內建 DNS
      port: ${REDIS_PORT:6379}
      timeout: 2000ms                 # 命令逾時
```

容器之間靠 `lucky-network` 這個 docker bridge network 的**服務名 DNS 解析**（`redis` → 容器 IP），不是 localhost。
這也是雷區 26 那個 `UnknownHostException: postgres` 的成因——容器與 network 脫鉤時 DNS 就解不出來。

### 5.4 序列化：刻意用 `StringRedisTemplate`

```java
private final StringRedisTemplate redisTemplate;   // TokenRedisService.java:21
```

不是 `RedisTemplate<Object,Object>`。**鍵值都是純字串**（`StringRedisSerializer`），**沒有 JDK 序列化**。三個理由：

1. `redis-cli` 可以直接 `GET` 讀懂，除錯不用解碼
2. **跨語言**——我們有 Node.js 的對帳／重建腳本（`tools/reconciliation/*.mjs`）要讀同一批 key
3. JDK 序列化有 class 版本綁定問題，改個欄位就反序列化失敗

### 5.5 最重要的：把多次往返壓成一支 Lua（全專案 5 支）

這正是「Redis 需要連線」的直接代價對策。**Lua 在 Redis 單執行緒內原子執行 = 免費的交易/CAS。**

**(1) Gateway 令牌桶限流** — `PlayerRateLimitGlobalFilter.java:59-86`
```lua
local last_tokens = tonumber(redis.call('GET', tokens_key))
if last_tokens == nil then last_tokens = capacity end
local delta  = math.max(0, now - last_refreshed)
local filled = math.min(capacity, last_tokens + (delta * rate))
local allowed = filled >= requested
redis.call('SET', tokens_key, new_tokens, 'EX', ttl)   -- token 與 TTL 同腳本原子寫入
redis.call('SET', ts_key, now, 'EX', ttl)
```
**舊版的三個 bug 一次修掉**：① `INCR` + `EXPIRE` 兩次往返，expire 一旦失敗 key 永無 TTL → **該玩家永久 429 且不自癒**；② 是固定視窗不是令牌桶，視窗邊界可在數毫秒內送出 2× 上限；③ 只讀 `burstCapacity`，`replenishRate` 是死設定。

**(2)(3)(4) 風控** — `RiskControlService.java:69-107`：inflight 取號（`INCR` + 僅首次 `PEXPIRE`）、釋放（`DECR` + 歸零即 `DEL`）、玩家日水位（`HINCRBY` × 2 + `PEXPIRE`）——全部從 2 往返壓成 1。

**(5) 捕魚 Session 樂觀鎖 CAS** — `FishingSessionStore.java:49-62`
```lua
local current = redis.call('HGET', KEYS[1], 'version')
if current ~= ARGV[1] then return 0 end       -- 版本不符，整批拒絕
for i = 3, #ARGV, 2 do redis.call('HSET', KEYS[1], ARGV[i], ARGV[i+1]) end
redis.call('PEXPIRE', KEYS[1], ARGV[2])
return 1
```
解決「讀→改→整包寫回」的**丟失更新**（ADR-008）。CAS 失敗 → 重讀 → 重放 → 重試，上限 3 次拋 409。

### 5.6 Redis 故障怎麼辦（分層降級策略，這題很加分）

| 元件 | 策略 | 理由 |
|---|---|---|
| Gateway 限流 | **fail-open 放行**（`PlayerRateLimitGlobalFilter.java:158-163`） | 真正的抗洪堤壩是 AIMD 在途上限（**純記憶體 `AtomicInteger`，不碰 Redis**）。不能讓限流元件把 Redis 故障放大成 gateway 全面中斷 |
| 風控 | **降級直查 DB** | 單一真相在 `game_rounds`，Redis 只是水位快取 |
| 捕魚 Session | **拋 409** | Session 是主儲存，沒有降級路徑 |

> **面試怎麼講**
> 「我們用 Lettuce 走 shared native connection 而不是連線池——Lettuce 是 Netty-based 執行緒安全，一條連線就能 pipeline；而 Redis 執行命令是單執行緒的，開池不提升它的處理能力。真正要對付的是『每個操作一次網路往返』，我們的做法是把多步操作壓成 Lua，全專案 5 支：限流令牌桶、風控三支、捕魚 session 的 CAS。而且降級策略是分層的——gateway 限流 fail-open，因為真正的堤壩是純記憶體的 AIMD；風控降級直查 DB；捕魚 session 沒有降級路徑就老實拋 409。」

## 6. 多級快取（L1 記憶體 + L2 Redis）：我們沒做，以及為什麼

### 6.1 事實：全 repo 搜 `@Cacheable` / `@EnableCaching` / `Caffeine` → **零命中**。我們是單層 Redis。

### 6.2 面試官在講的架構

```
請求 → L1: JVM 堆內 Map (Caffeine)   ~50–100 ns    ← 命中就直接回，不碰網路
         ↓ miss
       L2: Redis (TCP 往返)          ~0.1–0.5 ms（同機房）
         ↓ miss
       DB                            ~1–10 ms
```

**L1 的價值**：比 Redis 快 **1,000～10,000 倍**（記憶體讀 vs 網路往返）。熱點 key 每秒被讀幾萬次時，L1 能把 Redis QPS 砍掉 90%+。

**L1 的代價（關鍵）**：**多副本間的一致性**。每個 JVM 有自己的 L1——A 實例更新了 Redis，B 實例的 L1 還是舊值。要嘛靠 **Redis Pub/Sub 廣播失效**，要嘛靠**短 TTL 硬扛陳舊**。

### 6.3 逐 key 分析：為什麼我們的資料都不適合 L1

| Redis key | 性質 | 加 L1 會怎樣 |
|---|---|---|
| `rank:*` 排行榜 ZSET | **主儲存**（不是快取） | 快取一個主儲存 = 製造資料分裂 |
| `disabled:player:{id}` | 安全機制（後台停用封鎖） | **停用玩家在 L1 TTL 內還能繼續玩 → 安全漏洞** |
| `jwt:blacklist:{jti}` | 登出／撤銷 | 登出後 token 在 L1 TTL 內仍有效 → **安全漏洞** |
| `rate:{game,player}:{uid}:tokens` | 全域限流計數 | 每個 gateway 實例各有一份桶 → **限流直接失效** |
| `game:fishing:session:{playerId}` | Session 讀改寫狀態 | 製造丟失更新——我們才剛用 CAS 修掉這個問題（ADR-008） |
| **`risk:rtp:{gameType}`** | **唯一的純快取**（TTL 10s，可容忍陳舊） | 唯一適合，但排程每 2 秒才寫一次、讀取量不大，**收益趨近於零** |

**結論：沒加 L1 是設計選擇，不是疏漏。** 我們 Redis 裡**沒有一個 key 是「讀多寫少的熱點快取」**——那才是 L1 的適用對象（商品目錄、設定檔、賠率表、字典資料）。

### 6.4 但我們其實做過同樣的取捨——只是在別的地方

`RouteConcurrencyLimitGlobalFilter.java:31` 的註解：
> 計數是**單機記憶體 `AtomicInteger`（非 Redis）**：併發上限本質是「這台 gateway 實例的在途數」

這正是「**用記憶體換掉 Redis 往返**」的同一個決定，代價是「上限變成 per-instance 而非全域」。
拿這個當「我理解這個 trade-off」的證據。

### 6.5 如果要做，正確做法長怎樣

```java
// L1: Caffeine，小容量 + 短 TTL（短 TTL 是一致性的保險絲）
Caffeine.newBuilder()
    .maximumSize(10_000)
    .expireAfterWrite(Duration.ofSeconds(5))
    .build();

// L2: Redis
// 失效傳播：Redis Pub/Sub 廣播 invalidate 訊息，各實例收到就清自己的 L1
```

> **面試怎麼講**
> 「多級快取我理解，但我們刻意沒做 L1。判準是『這份資料能不能容忍陳舊』——L1 買延遲、付一致性，每個 JVM 一份，寫入要靠 Pub/Sub 廣播失效或短 TTL 硬扛。而我們 Redis 裡的東西，排行榜是主儲存、停用標記和 JWT 黑名單是安全機制、限流桶是全域計數、捕魚 session 是讀改寫狀態，全都禁不起陳舊。唯一的純快取是風控 RTP，但它每 2 秒才刷一次、讀取量不大，加 L1 沒有收益。如果哪天有商品目錄那種讀多寫少的熱點，我會用 Caffeine + Redis Pub/Sub 失效。」

## 7. 附帶戰績：`spring.task.scheduling.pool.size` 預設只有 1（我們盤查時抓到並修掉）

**這是一個「面試官問你最近抓到什麼問題」可以直接用的小故事，而且是自己盤查出來的、不是被 bug 打到的。**

### 現象

Spring Boot 的 `@Scheduled` 預設共用**一個只有 1 條執行緒**的 `ThreadPoolTaskScheduler`
（`spring.task.scheduling.pool.size` 預設 = 1），而我們四個服務都有多支排程擠在上面：

| 服務 | `@Scheduled` 數量 | 最痛的互卡 |
|---|---|---|
| game-service | **7** | `GlobalRtpCacheScheduler`（每 2 秒刷 `risk:rtp:*`，TTL 10 秒）被 `PlayerDayWaterlineReconcileScheduler`（掃全部玩家 DB 聚合＋逐列 Redis 寫）卡住 |
| wallet-service | 3 | `WalletOutboxPurgeJob`（每日 04:00 批次刪列）卡住 `WalletOutboxPoller`（每 200 ms 送 Kafka） |
| rank-service | 3 | 三支都在 00:00 觸發（週一三支同時），只能序列跑 |
| member-service | 2 | 同 wallet：purge 卡住 poller |

### 為什麼這是真問題（不是理論潔癖）

- **game-service**：`risk:rtp:*` 快取 TTL 只有 10 秒。刷新排程被卡超過 10 秒 → 快取過期 → 風控熱路徑**退回每局直查 DB 做 500 局聚合**，正是 T-090 Phase A1 花力氣消滅掉的 P99 主因，等於效能調校被悄悄回退。
- **wallet-service**：Outbox poller 是 wallet 事件的唯一出口。purge 跑多久，`wallet.credit`/`wallet.debit` 事件就**停發多久**——下游 MySQL 讀視圖、rank 排行、admin 報表**三方同時漂移**。

### 修法與安全論證

```yaml
spring:
  task:
    scheduling:
      pool:
        size: 4      # game；wallet/rank = 3、member = 2
```

**放大池安全嗎？** 兩件事要分清楚：

1. **同一支 `@Scheduled` 方法不會並行**——`ScheduledThreadPoolExecutor` 對同一個 task 保證不重疊執行（前一次沒跑完，下一次只會延後不會並行）。放大池**只讓「不同」排程彼此不互卡**。
2. **不同排程之間要驗資料交集**。我逐支確認過都不相交，例如 rank 的三支：

| 排程 | 讀 | 寫 |
|---|---|---|
| `DailyRankSnapshotService` | DB 錢包餘額 | DB `rank_daily_snapshots` |
| `RankService.resetDailyWinnings` | — | Redis `rank:daily:winnings`（DEL） |
| `WeeklyRankResetService` | Redis `rank:global:coins`、DB 餘額 | DB `rank_history`、重建 `rank:global:coins` |

三者交集為空，只是「同時觸發」不是「A 必須在 B 之前」，所以並行安全。

> **這一步不能跳**：如果三支之間真有順序依賴（例如快照必須在重置**之前**讀同一個 key），
> 那放大池就會把「靠序列執行僥倖正確」變成**競態**——修效能反而製造資料 bug。

### 和 §1 的連結（面試官如果串起來問）

如果哪天真的開了 `spring.threads.virtual.enabled: true`，Spring Boot 會把排程換成
`SimpleAsyncTaskScheduler`（每個任務一條虛擬執行緒、不受 `pool.size` 限制），**這個設定就自動失效了**。
也就是說：**這次的修正是「在平台執行緒世界裡的正確解」**，虛擬執行緒是另一條路。

> **面試怎麼講**
> 「最近我在盤查執行緒模型時發現，Spring 的 `@Scheduled` 預設共用一條執行緒，而我們 game-service 有 7 支排程擠在上面。最危險的是每 2 秒刷風控 RTP 快取那支——快取 TTL 只有 10 秒，一被慢排程卡住就過期，風控熱路徑會退回每局直查 DB 做 500 局聚合，等於把我們之前的效能調校悄悄回退掉。修法是設 `spring.task.scheduling.pool.size`，但我沒有直接改數字——先逐支確認不同排程動的資料互不相交。因為如果它們之間有順序依賴，放大池會把序列執行的僥倖正確變成競態，那是拿效能換資料正確性。」
